# Contributing to GOX

Thank you for your interest in contributing to GOX.

GOX recognizes that contributing to an open source project does not necessarily mean writing code. Bug reports, proposals for new features, and other contributions that materially help improve the project may be recognized as contributions.

At this stage of the project, GOX primarily accepts contributions through **bug reports** and **proposals**. Direct implementation and modification of the source code are handled by the project maintainers.

This model may evolve in the future as the project, its community, and its resources grow.

## Bug Reports

If you find incorrect behavior in GOX, you can report it through **GitHub Issues**.

A good bug report should include, when possible:

- A clear description of the problem.
- The expected behavior.
- The observed behavior.
- The steps required to reproduce it.
- The GOX version being used.
- Relevant information about the environment.
- A minimal example or reproduction code, when useful.
- Logs, error messages, or other information that may help investigate the problem.

A report that materially contributes to identifying, reproducing, or resolving an issue may be recognized as a contribution to the project.

The implementation of the fix will be handled by the GOX maintainers.

Issues that may have security implications **must not be published as public GitHub Issues**. See [`SECURITY.md`](SECURITY.md) for the reporting process using GitHub Private Vulnerability Reporting.

## Proposals

Proposals for new features, APIs, syntax, or significant changes to GOX behavior are welcome.

A proposal should clearly explain:

- The problem or need it is intended to address.
- The proposed behavior.
- Why it would be useful to GOX or its users.
- Examples that help explain the proposal, when necessary.

Proposals will be evaluated with consideration for the architecture, consistency, philosophy, and goals of GOX.

An accepted proposal does not necessarily mean that its original design will be implemented exactly as presented. The maintainers may adapt, modify, or redesign the solution to ensure that it integrates correctly with the rest of GOX.

When a proposal materially contributes to a feature that is ultimately incorporated into the project, its author may be recognized for their contribution.

The final implementation will be handled by the GOX maintainers.

## Code Contributions

At this stage, GOX **does not accept Pull Requests containing direct code contributions**.

Development and modifications to the source code are handled by the maintainers. This helps maintain a consistent architecture, API, syntax, and technical direction while the project is in its early stages.

This does not prevent contributors from including code as part of a bug report or proposal. Contributors may provide code examples, minimal reproducible cases, proofs of concept, or possible API and syntax designs when they help explain or demonstrate a contribution.

These examples are considered supporting material for evaluating and developing the contribution. The implementation ultimately incorporated into GOX will be designed and written by the maintainers.

The policy regarding direct code contributions and Pull Requests may change in the future as the project evolves.

## Recognition

GOX may recognize as contributors people who have made significant contributions to the project even if they did not directly write the code that is ultimately incorporated.

This may include, among other things:

- Bug reports that materially contribute to identifying or resolving an issue.
- Proposals that materially contribute to the design or introduction of a new feature.
- Other technical or documentation contributions that have a significant impact on the project.

Recognition of a contribution **does not imply authorship or ownership of code written by the GOX maintainers**.

## Security

Potential security vulnerabilities must not be reported through public GitHub Issues.

See [`SECURITY.md`](SECURITY.md) for the vulnerability reporting process using **GitHub Private Vulnerability Reporting**.
